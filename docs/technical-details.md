## 1. กันไม่ให้โมเดลโกง (data leakage)

"โกง" ในที่นี้คือโมเดลได้เห็นข้อมูลของอนาคตตอนเรียน ทำให้คะแนนตอนทดสอบสวยเกินจริง แต่พอใช้งานจริงแย่กว่านั้นมาก ป้องกัน 3 ชั้น:

- **แบ่งข้อมูลตามเวลา ไม่สุ่ม** เพราะระบบจริงต้องทำนายอนาคตจากอดีต

  | ชุด | ช่วงเวลา (ปี 2015) | จำนวน events | ใช้ทำอะไร |
  | --- | --- | --- | --- |
  | Train | 3 พ.ค. → 4 ก.ย. | 2,362,079 | สอนโมเดลและสร้างฟีเจอร์ |
  | Val | 4 ก.ย. → 11 ก.ย. (7 วัน) | 125,044 | จูนและตัดสินว่าโมเดลใหม่ดีกว่าเดิมไหม |
  | Test | 11 ก.ย. → 18 ก.ย. (7 วัน) | 108,673 | ดูผลสุดท้ายครั้งเดียว |

- **ฟีเจอร์เป็น point-in-time** ทุกฟังก์ชันรับเวลา `as_of` และใช้เฉพาะ event ที่เกิดก่อนเวลานั้น มี test ที่เติม event อนาคตเข้าไปแล้วผลต้องไม่เปลี่ยน (ผมลองแก้โค้ดให้รั่วแล้ว test ล้มจริง)
- ค่า `category` และ `available` ของสินค้าใช้ค่า "ที่เป็นอยู่ ณ เวลานั้น" ไม่ใช่ค่าล่าสุดทั้งไฟล์
- **Test set ถูกกันไว้ ยังไม่ได้ประเมินโดยตั้งใจ** จะดูครั้งเดียวกับโมเดลสุดท้าย เพื่อไม่ให้ปรับโมเดลเข้าหาข้อสอบ

## 2. วิธีวัดผล

- **Ground truth** = สินค้าที่ผู้ใช้ใส่ตะกร้าหรือซื้อในช่วงนั้น (การดูเฉยๆ ไม่นับ เพราะเป็นสัญญาณอ่อน)
- **ตัวชี้วัด:** Recall@K, Hit@K, NDCG@K, MAP@K, Coverage@K ทุกค่ามี **ช่วงความเชื่อมั่น 95%** (bootstrap ข้ามผู้ใช้) เพราะผู้ใช้ที่วัดได้มีแค่ ~1.9K คน ตัวเลขจึงแกว่ง
- **แยก warm / cold:** warm = ผู้ใช้ที่เคยอยู่ในข้อมูลเรียน, cold = ไม่เคยเห็น ผู้ใช้ส่วนใหญ่เป็น cold จึงต้องรายงานแยก ไม่งั้นค่าเฉลี่ยจะบังปัญหา
- **เทียบกับ baseline:** `random`, `popular_all`, `popular_7d` (สินค้ายอดนิยมที่ถ่วงน้ำหนัก view 1 / addtocart 3 / transaction 5) โมเดลต้องชนะ baseline ที่ไม่ฉลาดเหล่านี้ให้ได้

## 3. ฟีเจอร์ 38 ตัว

โค้ดอยู่ที่ [src/features/](../src/features/) และรายการทั้งหมดอยู่ที่เดียวคือ [spec.py](../src/features/spec.py)

| กลุ่ม | จำนวน | ตัวอย่าง |
| --- | --- | --- |
| user | 11 | จำนวน view/cart/buy, sessions, ห่างจาก event ล่าสุดกี่วัน, ความสนใจที่ค่อยๆ จางตามเวลา |
| item | 16 | ความนิยม 1/7/28 วัน, แนวโน้ม, จำนวนผู้ใช้ที่ไม่ซ้ำ, อายุสินค้า, อัตราใส่ตะกร้า/ซื้อแบบ smoothed, หมวด, มีของไหม |
| category | 3 | ความนิยมของหมวด |
| pair (user × item) | 5 | ผู้ใช้เคย view/cart/buy สินค้านี้กี่ครั้ง, ห่างกี่วัน, สัดส่วนหมวดที่ผู้ใช้สนใจ |
| candidate | 3 | คะแนน ALS, อันดับที่ดึงมา, ดึงจาก ALS หรือสำรอง |

**ให้ฟีเจอร์ตอนเทรน = ตอนใช้งานจริง (offline = online):** ฟีเจอร์ผู้ใช้แยกเป็น *state* (นับ, เวลาแรก/ล่าสุด, ผลรวมที่เสื่อมตามเวลา, 20 สินค้าล่าสุด ซึ่งอัปเดตทีละ event ได้) กับ *derive* (recency, ratio คำนวณตอนใช้) เพื่อไม่เก็บค่าที่เก่าทันทีที่เขียน รายการฟีเจอร์สร้าง Pandera schema และ `schema.json` ที่เซฟคู่โมเดลอัตโนมัติ ตอนให้บริการจะปฏิเสธโมเดลที่ลำดับฟีเจอร์ไม่ตรง

## 4. โมเดลสองขั้น

1. **ALS** (`implicit`) ดึง candidate 200 ตัวต่อผู้ใช้จาก interaction ที่ถ่วงน้ำหนัก ตอนให้บริการคำนวณด้วย dot product ใน numpy (ไม่ต้องมี `implicit`) จูน hyperparameter 12 ชุด ได้ factors 128 / regularization 0.01 / alpha 40
2. **Ranker** (LightGBM LambdaRank) เรียง 200 ตัวนั้นใหม่ด้วยฟีเจอร์ 38 ตัว เทรนบน 4 snapshot ต่อเนื่อง (ฟีเจอร์จากอดีต, คำตอบคือสิ่งที่ผู้ใช้ทำใน 7 วันถัดมา) ผู้ใช้ที่ ALS ไม่รู้จักได้ candidate เป็นสินค้ายอดนิยม 7 วันล่าสุด
3. **Evaluation gate:** โมเดลใหม่ต้องมี NDCG@10 ดีกว่า champion เดิม (หรือ baseline ถ้ายังไม่มี) และ Recall@200 ไม่แย่ลง จึงลงทะเบียนใน MLflow Registry และย้าย alias `champion` bundle ที่เก็บประกอบด้วยโมเดล, `schema.json`, รายการ popular พร้อม tag ของ git commit และ hash ของข้อมูล

**ทำไมเป็นสองขั้น:** ดึง candidate ด้วยโมเดลเบา (ALS) จากสินค้าราว 160K ตัว แล้วใช้โมเดลที่ฉลาดกว่าเรียงเฉพาะ 200 ตัว ได้ทั้งความเร็วและคุณภาพ และ Ranker ใช้ฟีเจอร์ที่ ALS ใช้ไม่ได้ เช่น "ผู้ใช้เคยใส่ตะกร้าสินค้านี้"

## 5. ระบบออนไลน์

```text
GET /recommend?user_id=..  ->  Redis (1 รอบ: state, จำนวนต่อสินค้า, จำนวนต่อหมวด, clock)
                           ->  candidate 200 ตัว (ALS dot product / popular list)
                           ->  ฟีเจอร์ 38 ตัว  ->  LightGBM  ->  top-k + model_version + source
```

- **Event-time clock:** ข้อมูลเป็นปี 2015 ถ้าใช้เวลาเครื่อง recency จะเป็น ~4,000 วันและค่าที่เสื่อมตามเวลาเป็น 0 ทุกคน จึงเก็บเวลาของ event ล่าสุดไว้ใน Redis แล้วคำนวณฟีเจอร์ ณ เวลานั้น
- **เริ่มจากจุดเดียวกับ champion:** โหลด state ณ `val_start` เข้า Redis (1.28 ล้านผู้ใช้ ใน 28 วินาที ใช้ RAM ~720 MB) แล้ว replay เฉพาะ event หลังจากนั้น `make replay` ล้าง Redis ก่อนทุกครั้งจึงไม่นับซ้ำ
- **Streaming ที่ไม่นับซ้ำ:** Kafka ส่งอย่างน้อยหนึ่งครั้ง (หลัง crash จะอ่าน batch เดิมซ้ำ) consumer จึงเก็บ offset ล่าสุดที่ใช้ไว้ใน Redis ใน transaction เดียวกับการอัปเดต state ตอนทดสอบ kill consumer กลางทาง ก่อนแก้นับ event ซ้ำกับผู้ใช้ 343 คน หลังแก้ตรวจทั้ง 1.4 ล้านคนแล้วผิด 0 คน
- **ทางสำรอง:** Redis ช้า/ล่ม (timeout 50 ms) → ตอบโดยไม่มีฟีเจอร์ผู้ใช้ (`degraded: true`) · Ranker พัง → ตอบ popular list (`source: popular_fallback`) · ผู้ใช้ใหม่ → candidate จาก popular
- **Hot reload:** `POST /admin/reload` สร้างโมเดลใหม่ให้เสร็จและตรวจก่อนสลับ ถ้า bundle เสีย (ลำดับฟีเจอร์ไม่ตรง หรือ snapshot ไม่ตรง) ตอบ 409 และใช้โมเดลเดิมต่อ ถอยเวอร์ชันได้โดยย้าย alias แล้ว `make pull-model`
- **ใช้ผลซ้ำอย่างปลอดภัย:** ผู้ใช้ใหม่ที่ไม่มีประวัติทุกคนได้ candidate และฟีเจอร์ชุดเดียวกัน จึงคำนวณรายการเรียงลำดับครั้งเดียวต่อโมเดล (test ยืนยันว่าคำตอบเท่าเดิมทุก k)

## 6. พิสูจน์ว่าถูกต้อง

- **offline = online** ทดสอบบนข้อมูลสังเคราะห์ (ฟีเจอร์จาก Redis ที่เติมด้วย stream เท่ากับฟีเจอร์ offline) และบนโมเดล champion จริงกับผู้ใช้ 120 คน (ฟีเจอร์และลำดับที่ API แนะนำเท่ากับเส้นทางตอนเทรนทุกตัว)
- **ทดสอบ mutation:** แก้สูตรให้ผิดโดยตั้งใจแล้วตรวจว่า test ล้ม (เช่น สูตร decay, สัดส่วนหมวด, การกรองอนาคต)
- **ทดสอบความทนทาน:** kill consumer กลางการ replay, reload ด้วย bundle เสีย, เปลี่ยนทุกค่าใน `.env`
- **ทดสอบ API ด้วย Postman:** 19 request, 95 assertions ดู [api-testing.md](api-testing.md)

## 7. Load test และ Monitoring

- **Prometheus** เก็บ latency (histogram), RPS, error, แหล่งที่มาของคำตอบ, เวลาอ่าน Redis, CPU/RAM, Kafka lag · **Grafana** มี dashboard ที่สร้างอัตโนมัติจากไฟล์
- **k6 สามแบบ:** smoke (1 VU) · load (ไต่ถึง 100 VUs แล้วค้าง, เกณฑ์ p95 < 100 ms และ error < 1%) · stress (เพิ่มอัตรา request ไปเรื่อยๆ แบบ open model เพื่อให้เห็นอาการล้นจริง)
- **user id สมจริง:** 15% ผู้ใช้ที่ ALS รู้จัก, 35% มีประวัติใน Redis, 50% ผู้ใช้ใหม่ ไม่ใช่เลขสุ่มล้วน
- **ปรับปรุงตามหลักฐาน:** วัด baseline → ดูกราฟ/profile หาคอขวด → แก้ → วัดซ้ำด้วยชุดทดสอบเดิม (เจอ thread ของ numpy/LightGBM แย่งกัน และการสร้าง DataFrame ต่อ request เป็นคอขวด) ขั้นตอนและกราฟทุกรอบอยู่ใน [loadtest.md](loadtest.md)

## 8. การตัดสินใจออกแบบและราคาที่จ่าย

| การตัดสินใจ | เหตุผล | ราคาที่จ่าย |
| --- | --- | --- |
| โมเดลสองขั้น (ALS + Ranker) | เร็วและแม่น Ranker ใช้ฟีเจอร์ที่ ALS ใช้ไม่ได้ | ต้องดูแลสองโมเดลที่เวอร์ชันตรงกัน (เก็บเป็น bundle เดียว) |
| แบ่งตามเวลา ไม่สุ่ม | จำลองการทำนายอนาคตจริง กัน leakage | ผู้ใช้ใน Val/Test ส่วนใหญ่เป็นผู้ใช้ใหม่ (สมจริงแต่ ALS วัดผลได้ยาก) |
| Kafka แทนเขียน Redis ตรง | แยกส่วนกัน, เรียงตามผู้ใช้, replay ได้, ปรับขนาดได้ | ซับซ้อนขึ้น และต้องกันการนับซ้ำเอง (เก็บ offset ใน Redis) |
| เก็บ hash จำนวนต่อสินค้าใน Redis | ให้ pair features ตอนให้บริการตรงกับตอนเทรน (แผนเดิมเก็บแค่ 20 ชิ้นล่าสุด) | ใช้ RAM มากขึ้น (~720 MB) |
| ไม่ใช้ TTL ใน Redis (แผนเดิมมี) | state ที่หมดอายุทำให้ฟีเจอร์ online ต่างจากตอนเทรน | Redis โตขึ้นเรื่อยๆ ในระบบจริงต้องมีนโยบายเก็บกวาดแบบอื่น |
| Event-time clock | ข้อมูลเป็นปี 2015 | ต้องส่งเวลาของ event มาด้วยเสมอ |
| ฟีเจอร์ผู้ใช้เป็น Python ล้วนตอนให้บริการ | polars แถวเดียวกิน ~1 ms ต่อ request | มีสูตรสองชุด จึงมี test เทียบกับโค้ด offline ทุกครั้ง |
| MLflow บนเครื่อง (SQLite) ไม่อยู่ใน compose | เรียบง่าย ไม่ต้องมี server | ผู้อื่นใช้ร่วมกันไม่ได้ `make pull-model` คัดลอก bundle ไปให้ container |
| ตั้งค่าผ่าน `.env` | ไม่ฝังค่าใน image เปลี่ยนได้โดยไม่ rebuild | ต้องมี `.env` (สร้างจากแม่แบบด้วย `make env`) |
