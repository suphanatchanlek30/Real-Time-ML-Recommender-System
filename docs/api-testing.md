# ทดสอบ API ด้วย Postman (สำหรับคนที่ไม่เคยใช้)

คู่มือนี้พาลองยิง API ของระบบแนะนำสินค้าด้วยตัวเอง และเช็กว่าทำงานถูกต้องด้วย **test case ที่เตรียมไว้ให้แล้ว 19 ข้อ (95 การตรวจ)** ไม่ต้องเขียนโค้ดเอง

## เข้าใจก่อนเริ่ม

| คำ | หมายถึง |
| --- | --- |
| **API** | "หน้าต่างรับออเดอร์" ของระบบ เราส่งคำขอไป (เช่น "ขอสินค้าแนะนำให้ผู้ใช้เบอร์ 9145") แล้วระบบตอบกลับมาเป็นข้อมูล |
| **Postman** | โปรแกรมสำหรับส่งคำขอไปหา API และดูคำตอบ โดยไม่ต้องเขียนโค้ด |
| **Request** | คำขอ 1 ครั้ง ใน Postman จะเห็นเป็นรายการหนึ่งบรรทัด |
| **Collection** | กลุ่มของ request ที่เตรียมไว้ (ของเราชื่อ **Recommender API**) |
| **Environment** | ที่เก็บตัวแปร เช่น ที่อยู่ของ API และเลขผู้ใช้ตัวอย่าง (ของเราชื่อ **local**) |
| **Test** | ข้อตรวจที่ Postman ตรวจคำตอบให้อัตโนมัติ เช่น "ต้องได้ 10 รายการ" ผ่านเป็น ✓ เขียว ไม่ผ่านเป็น ✗ แดง |

**ที่ผมเตรียมให้:** โฟลเดอร์ [postman/](../postman/) มี 2 ไฟล์ คือ collection และ environment

## ขั้นที่ 1: เปิดระบบก่อน

API ต้องรันอยู่ ถึงจะมีอะไรให้ Postman ยิง (ถ้ายังไม่เคยเทรนโมเดล ดู [runbook-training.md](runbook-training.md) ก่อน)

```bash
make pull-model && make up     # ดึงโมเดลและเปิดระบบ
make replay                    # โหลดข้อมูลผู้ใช้เข้าระบบ (~3 นาที) หรือ make load-redis (~30 วินาที)
curl localhost:8000/health     # ต้องเห็น {"status":"ok", ...}
```

> ⚠️ ระบบจำข้อมูลผู้ใช้ไว้ในหน่วยความจำ ทุกครั้งที่ปิดแล้วเปิดใหม่ต้องรัน `make replay` (หรือ `make load-redis`) อีกครั้ง ไม่งั้นผู้ใช้ทุกคนจะเหมือนผู้ใช้ใหม่ และ test ข้อ "ผู้ใช้ที่ระบบรู้จัก" จะไม่ผ่าน

## ขั้นที่ 2: นำเข้าไฟล์เข้า Postman

1. กด **⌘ + O** (Mac) หรือ **Ctrl + O** (Windows) หน้าต่าง Import จะขึ้น (ถ้าหาไม่เจอ ให้ดูไอคอนข้างปุ่ม `+` เหนือคำว่า COLLECTIONS ในแถบซ้าย)
2. เปิดโฟลเดอร์ `postman/` ในโปรเจกต์ แล้ว **ลากไฟล์ทั้งสองลงในหน้าต่าง Import**
   - `recsys.postman_collection.json`
   - `local.postman_environment.json`
3. กด **Import** ในแถบซ้ายจะเห็น **Recommender API** (มี 4 โฟลเดอร์)
4. มุมขวาบนมีกล่องเขียนว่า **No Environment** หรือ **New Environment** กดแล้วเลือก **local**

> ถ้าเคย import ไฟล์เก่าไปแล้ว ให้คลิกขวา Recommender API → Delete แล้ว import ไฟล์ใหม่อีกครั้ง

## ขั้นที่ 3: ลองยิง 1 request

1. คลิกที่ **Known user (ALS knows them), k=10** ในแถบซ้าย
2. กดปุ่ม **Send** สีน้ำเงินมุมขวาบนของ request
3. ดูด้านล่างของหน้าจอ:

| ส่วน | เห็นอะไร |
| --- | --- |
| **Body** | คำตอบของ API (ดูตัวอย่างด้านล่าง) |
| **Test Results** | รายการ test เป็น ✓ เขียว (ผ่าน) หรือ ✗ แดง (ไม่ผ่าน) |
| มุมบนของส่วนล่าง | รหัสสถานะ **200 OK** (ตอบสำเร็จ) และเวลาที่ใช้ เช่น `9 ms` |

**ตัวอย่างคำตอบจริงจากระบบ** (ขอ 3 ชิ้น: `GET /recommend?user_id=9145&k=3`):

```json
{
  "items": [
    {"item_id": 350790, "score": 0.9994},
    {"item_id": 283100, "score": 0.6493},
    {"item_id": 59399,  "score": 0.2448}
  ],
  "model_version": "1",
  "source": "ranker",
  "retrieval": "als",
  "degraded": false
}
```

อ่านได้ว่า: **ระบบแนะนำสินค้ารหัส 350790 เป็นอันดับ 1** (คะแนนยิ่งสูงยิ่งน่าสนใจ) ตามด้วย 283100 และ 59399

| ช่อง | ความหมาย |
| --- | --- |
| `items` | สินค้าที่แนะนำ เรียงจากน่าสนใจที่สุดไปน้อยสุด (`item_id` = รหัสสินค้า, `score` = คะแนน) |
| `model_version` | โมเดลเวอร์ชันที่ใช้ตอบ |
| `source` | `ranker` = โมเดลเรียงลำดับให้ตามปกติ · `popular_fallback` = โมเดลมีปัญหา ระบบเลยตอบสินค้ายอดนิยมแทน |
| `retrieval` | `als` = ระบบรู้จักผู้ใช้คนนี้ดี · `popular` = ไม่รู้จัก เลยเริ่มจากสินค้ายอดนิยม |
| `degraded` | `false` ปกติ · `true` = ระบบเก็บข้อมูลผู้ใช้ติดขัด จึงตอบโดยไม่ได้ดูประวัติของเขา |

## ขั้นที่ 4: รันทั้งหมดทีเดียว

คลิกขวาที่ **Recommender API** → **Run collection** → **Run** รอไม่กี่วินาทีจะได้สรุป ควรเป็น **19 request ผ่านทั้งหมด** (ทุก request ทำงานได้เองไม่ขึ้นกับลำดับ)

## Test case แต่ละข้อ ทำอะไร

### 1. Health and metrics: ระบบยังมีชีวิตอยู่ไหม

| Request | ทำอะไร | ผ่านเมื่อ |
| --- | --- | --- |
| Health | ถามสถานะระบบ | `status: ok`, มีเวอร์ชันโมเดล, ต่อฐานข้อมูลผู้ใช้ได้ |
| Metrics | ขอตัวเลขสถิติ (ที่ Prometheus เก็บ) | เป็นข้อความสถิติ มีตัวนับ request, latency, แหล่งที่มาของคำตอบ |

### 2. Recommend: ขอสินค้าแนะนำ

| Request | ทำอะไร | ผ่านเมื่อ |
| --- | --- | --- |
| Known user (ผู้ใช้ 9145) | ผู้ใช้ที่ระบบรู้จักดี | ได้ 10 ชิ้นพอดี, เรียงคะแนนถูก, ไม่ซ้ำ, `retrieval: als`, ตอบเร็วกว่า 250 ms |
| Known user again | ถามซ้ำอีกรอบ | ได้ 10 ชิ้นเดิมเรียงเหมือนเดิมเป๊ะ |
| User with history but unknown to ALS (ผู้ใช้ 10025) | ผู้ใช้ที่มีประวัติน้อย | `retrieval: popular` แต่ยังเรียงตามประวัติของเขา |
| Brand-new user (ผู้ใช้ 99999999) | ผู้ใช้ใหม่ที่ไม่เคยเห็น | ได้สินค้ายอดนิยมเรียงให้ |
| Another brand-new user (88888888) | ผู้ใช้ใหม่อีกคน | ได้รายการเดียวกับผู้ใช้ใหม่คนแรก (เพราะไม่มีข้อมูลต่างกัน) |
| k=1 / k=100 / k omitted | `k` คือจำนวนที่ขอ | ได้ 1 / 100 / 10 ชิ้น (ไม่ใส่ `k` = 10) |
| k=5 is the top of k=10 | เช็กความสอดคล้อง | 5 ชิ้นแรกต้องตรงกับ 5 ชิ้นแรกของ k=10 |

### 3. Input validation: ส่งข้อมูลผิดๆ ไปลองให้ระบบ

ทุกข้อต้องได้ **422** พร้อมคำอธิบายว่าผิดตรงไหน ไม่ใช่ระบบพัง (500)

| Request | ส่งอะไรไป |
| --- | --- |
| k=0 / k=101 | จำนวนที่ขอต่ำหรือสูงเกินกำหนด (1-100) |
| negative user_id | เลขผู้ใช้ติดลบ |
| user_id that is not a number | `user_id=abc` |
| missing user_id | ไม่ใส่ `user_id` เลย |

ตัวอย่างคำตอบเมื่อส่ง `k=0`: `{"detail":[{"msg":"Input should be greater than or equal to 1", ...}]}`

### 4. Admin: สั่งโหลดโมเดลใหม่

| Request | ทำอะไร | ผ่านเมื่อ |
| --- | --- | --- |
| Reload (token ถูก) | สั่งให้ระบบโหลดโมเดลอีกครั้งโดยไม่ต้องปิดเปิด | 200 บอกเวอร์ชันก่อนหน้าและปัจจุบัน |
| Reload (token ผิด) | ส่งรหัสผิด | **403** ถ้าตั้งรหัส `ADMIN_TOKEN` ไว้ใน `.env` · ได้ 200 ถ้ายังไม่ได้ตั้ง (ปกติ) |
| Recommendations still work after the reload | แนะนำสินค้าอีกครั้งหลัง reload | ยังทำงานตามปกติ |

ตัวแปรใน environment ที่แก้ได้: `known_user`, `history_user`, `new_user`, `new_user_2` (เลขผู้ใช้ตัวอย่าง), `admin_token` (รหัสของ reload) และ `base_url` (ที่อยู่ API ถ้าเปลี่ยนพอร์ตใน `.env`) ถ้าเปลี่ยน `known_user` ให้ใช้ผู้ใช้ที่ระบบรู้จักจริง

## ถ้าติดปัญหา

| อาการ | สาเหตุและวิธีแก้ |
| --- | --- |
| ขึ้น `Could not get response` / `ECONNREFUSED` | ระบบไม่ได้รันอยู่ ลอง `curl localhost:8000/health` ถ้าไม่ตอบ ให้รัน `make up` |
| ขึ้น ✗ ที่ "retrieval ต้องเป็น als" หรือ "ผู้ใช้ที่ระบบรู้จัก" | ยังไม่ได้โหลดข้อมูลผู้ใช้ รัน `make replay` (หรือ `make load-redis`) |
| `{{base_url}}` ไม่ถูกแทนที่ / ส่งไปที่แปลกๆ | ยังไม่ได้เลือก environment **local** ที่มุมขวาบน |
| Reload ได้ 403 ทั้งสองข้อ | ตั้ง `ADMIN_TOKEN` ใน `.env` ไว้ ให้ใส่ค่าเดียวกันในตัวแปร `admin_token` |
| หา Import ไม่เจอ | กด ⌘ + O หรือดูหัวข้อ "ขั้นที่ 2" |
| ไม่มี Postman | ใช้คำสั่งด้านล่างแทนได้ |

## ทางเลือกอื่นถ้าไม่อยากใช้ Postman

**1. รันจากเทอร์มินัล** (รัน test ชุดเดียวกันทั้ง 19 ข้อ ไม่ต้องติดตั้งอะไรเพิ่ม):

```bash
make api-test
```

**2. ใช้ curl ยิงทีละข้อ:**

```bash
curl "localhost:8000/recommend?user_id=9145&k=10"        # ผู้ใช้ที่ระบบรู้จัก
curl "localhost:8000/recommend?user_id=99999999&k=10"    # ผู้ใช้ใหม่
curl -i "localhost:8000/recommend?user_id=9145&k=0"      # ส่งค่าผิด ได้ 422
curl -X POST localhost:8000/admin/reload                 # โหลดโมเดลใหม่ (ใส่ -H "X-Admin-Token: ..." ถ้าตั้งรหัสไว้)
```

**3. เปิดหน้าเอกสารของ API ในเบราว์เซอร์:** <http://localhost:8000/docs> มีปุ่ม "Try it out" ให้กดทดลองยิงได้เลย โดยไม่ต้องติดตั้งอะไร

## ลองเพิ่มเอง (ไม่อยู่ใน collection)

| อยากลอง | ทำอย่างไร | คาดว่าจะเห็น |
| --- | --- | --- |
| ผลแนะนำเปลี่ยนตามพฤติกรรมสด | เรียก `/recommend?user_id=9145` แล้วรัน `make replay` ให้จบ แล้วเรียกซ้ำ | ลำดับสินค้าเปลี่ยนเล็กน้อย และ `event_clock` ใน `/health` ขยับเป็น 2015-09-18 |
| ข้อมูลผู้ใช้ขัดข้อง | `docker compose stop redis` แล้วเรียก `/recommend` | ยังตอบ 200 แต่ `degraded: true` (เปิดคืนแล้วต้อง `make load-redis` อีกครั้ง) |
| ตั้งรหัสป้องกัน reload | ใส่ `ADMIN_TOKEN=secret` ใน `.env` แล้ว `make up` ใส่ค่าเดียวกันใน `admin_token` | reload ด้วยรหัสผิดได้ 403 |
| ดูตัวเลข | เปิด Grafana <http://localhost:3000> ระหว่างรัน collection หลายรอบ | เห็น request และ latency ขึ้นใน dashboard |

กรณีข้อมูลผู้ใช้ขัดข้องและรหัสป้องกัน ครอบคลุมด้วย unit test แล้ว แต่ยังไม่ได้ลองกับระบบจริงในเอกสารนี้
